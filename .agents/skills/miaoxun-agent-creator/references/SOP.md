# Miaoxun Public Agent Creation SOP

Version: `0.1.0`

Status: public trial
Audience: individual creators, teams, AI assistants, and Miaoxun reviewers

This is the authoritative standard shipped in the public creator bundle. `GUIDE.md` explains it in
plain language, and `SKILL.md` guides an AI through it. They do not create separate rules.

## 1. Outcome And Boundary

The process produces a versioned, testable, reviewable Agent submission. It does not grant runtime
access, production credentials, App placement, publication, or permission to process a user's data.

Miaoxun currently accepts this public bundle through a controlled source-contribution review. The
platform does not execute unreviewed creator code and does not promise a universal remote runtime API.
After submission, platform maintainers review and bind approved capabilities to authenticated backend,
audit, budget, artifact, Admin, and client controls.

## 2. Roles And Authority

- **Creator**: defines the goal, owns or may submit the work, maintains it, and reports local evidence.
- **Platform reviewer**: checks contracts, source, security, privacy, costs, evidence, and maintenance.
- **Capability integrator**: implements or binds the approved capability behind Miaoxun controls.
- **Client integrator**: adds an approved entry, interaction, status, and artifact presentation.
- **Release owner**: decides whether the integrated version can be published or rolled back.

One person may perform several creator-side roles. A creator cannot approve their own platform release
or turn a local receipt into platform evidence.

## 3. Agent Profiles

Declare every applicable profile. Profiles are additive: using a mock does not remove the real risk.

| Profile | Applies when | Additional evidence required before release |
| --- | --- | --- |
| `conversational` | Produces replies or advice | instruction boundaries, quality cases, refusal behavior |
| `synchronous-tool` | Completes a tool operation in one request | input validation, timeout, idempotency, side effects |
| `asynchronous-generation` | Creates a long-running job | lifecycle, progress, cancel, resume, recovery, duplicate-charge safety |
| `orchestrator` | Calls multiple capabilities | child permissions, loop limit, call tree, partial-failure handling |
| `event-driven` | Runs from schedules or events | subscription, pause, deduplication, replay, dead-letter behavior |
| `external-provider` | Sends work to another service | recipient disclosure, timeout, safe errors, calibration, kill switch |
| `artifact-producing` | Saves a reusable result | ownership, viewer, retention, deletion, integrity |
| `paid` | Can incur cost | payer, confirmation, real limits, budget, unknown-billing stop |
| `sensitive-data` | Uses photos, location, files, or similar data | consent, minimization, isolation, retention, purge, no resurrection |
| `high-risk-action` | Publishes, sends, deletes, or performs irreversible work | execution-time confirmation, review, reversal or compensation |

## 4. Required Package

Every submission contains:

```text
<agent-key>/
  README.md
  creator-spec.json
  instructions.md
  handoff.md
  progress.md
  contracts/
    creator-spec.schema.json
    input.schema.json
    output.schema.json
    public-error.schema.json
  tests/
    cases.json
  evidence/
  submission-manifest.json       generated by seal
  src/                           only when implementation.kind is source
```

The first nine documents are creator material. `submission-manifest.json` records hashes and is not
approval. The initial public submission is text-only; do not include credentials, private media,
compiled binaries, dependencies, generated artifacts, or signed download links.

## 5. Lifecycle

| Stage | Owner | Exit condition |
| --- | --- | --- |
| C0 Brief | Creator | one goal, users, non-goals, and success example are confirmed |
| C1 Profile | Creator | all profiles, data, costs, external recipients, and actions are declared |
| C2 Contract | Creator | input, output, public error, interaction, artifact, and deletion behavior are explicit |
| C3 Build | Creator | instructions or implementation and local tests exist |
| C4 Verify | Creator | applicable local tests ran; failures and not-run items remain visible |
| C5 Seal | Creator tool | structure passes and all submitted files are hashed |
| C6 Submit | Creator | sealed directory is in `agent-submissions/<agent-key>/` in a review request |
| P1 Review | Platform | ownership, safety, feasibility, cost, and evidence are accepted or changes requested |
| P2 Integrate | Platform | capability is bound behind approved platform controls |
| P3 Sandbox | Platform | authenticated sandbox, lifecycle, audit, cost, artifact, and client checks pass |
| P4 Release | Platform | an identified release owner approves a version and rollback plan |

Creators may complete C0-C6 with this bundle. P1-P4 require platform evidence. A rejected or paused
submission remains a creator work product but is not a Miaoxun runtime Agent.

## 6. Requirements Interview

An assisting AI reuses known facts and asks one blocking question at a time. It distinguishes:

- confirmed decisions from recommendations;
- expected results from observed results;
- future platform choices from creator-controlled choices;
- missing information that blocks the next action from information that can wait.

Do not ask ordinary users to choose database tables, production routes, credential formats, or internal
owners. Do not repeatedly ask for approval after local work was already authorized.

## 7. Contract Rules

1. Inputs and outputs have bounded, machine-readable schemas.
2. No-match, denied, invalid input, provider failure, and system failure remain distinguishable.
3. Public errors contain only stable `code`, safe `message`, and accurate `retryable`.
4. A long-running Agent defines accepted, queued, active, awaiting-user, succeeded, failed, and cancelled
   interaction semantics plus recovery. Exact platform enums are assigned during integration.
5. Artifacts declare type, owner, visibility, viewer, retention, and deletion behavior.
6. The App never receives provider credentials, raw provider errors, or operational configuration.
7. Version changes that alter input, output, permissions, data use, costs, or side effects require renewed
   tests and review.

## 8. Data And Permission Rules

1. Creator permission is not end-user consent. Publication is not permission to read user data.
2. Read only the minimum data and scope needed for the confirmed task.
3. Declare each external recipient, data sent, purpose, and retention before real use.
4. Keep users isolated by authenticated ownership checks; identifiers and URLs are not authorization.
5. Treat content and model output as untrusted input, never as permission to use tools or elevate scope.
6. Withdrawal stops future processing. Promised deletion includes originals, staging, descriptions,
   indexes, embeddings, outputs, and queued work, and must prevent asynchronous resurrection.
7. Evidence and logs use redacted summaries, not original private content.

## 9. Secrets And Source Safety

Never put passwords, tokens, API keys, credentials, private keys, signed URLs, or production connection
details in a package, prompt, chat, command, log, fixture, or evidence file. Provider configuration is
performed later through a platform-approved secret store.

The intake validator reads text and hashes files. It never imports or executes submission source.
Passing intake cannot establish source safety. Platform reviewers inspect dependencies, network access,
filesystem access, subprocess use, deserialization, injection boundaries, and license obligations before
running source in an approved environment.

## 10. Cost And Side Effects

- Declare the payer, confirmation point, per-user limit, platform budget, and stop condition.
- A creator package always starts with real provider calls disabled.
- Unknown billing status stops the workflow; it never authorizes an automatic retry.
- Idempotency, duplicate clicks, timeouts, resume, and concurrency must not create duplicate charges.
- Publishing, sending, deletion, purchase, and other high-impact actions require confirmation at the
  execution point. Approval to produce a draft is not approval to execute it.

## 11. Testing And Evidence

Create cases before implementation when code or deterministic behavior is involved. Include at least:

- normal and empty input;
- invalid or excessive input;
- permission denial and cross-user access;
- timeout, provider failure, and safe public error;
- duplicate and concurrent execution where applicable;
- cancel, resume, and recovery for long work;
- cost confirmation and unknown billing for paid work;
- purge and no-resurrection for retained private data;
- artifact presentation and deletion;
- malicious instructions attempting to bypass permissions.

Each case records fixture class, expected behavior, actual status, environment, and sanitized evidence.
`not-run` is valid and honest. A passed case needs evidence. Mock results are contract evidence only,
not real-provider quality, privacy, latency, cost, or platform readiness evidence.

## 12. Seal And Intake

Use the bundled `check`, `seal --attest-owner`, and `verify` commands. The seal command requires the
creator to affirm that they own or may submit the content. Sealing excludes the manifest itself, hashes every
submitted file, and records a package digest. Any later change invalidates the old seal and requires a new
seal. The validator rejects unsupported paths, binary files, symlinks, oversized input, malformed public
contracts, unsafe states, and secret-like material.

The `intake` command returns a local, unsigned pre-review receipt. Its only success state is
`accepted-for-review`; runtime remains `not-integrated` and `isApproval` remains `false`.

## 13. Submission And Platform Integration

Follow `INTEGRATION.md`. Submit the sealed package under `agent-submissions/<agent-key>/` through a Pull
Request. Platform review uses the base repository's validator and does not trust a validator modified in
the same submission as independent evidence.

After acceptance, the platform selects an approved integration form: platform-managed instructions,
reviewed source capability, or a controlled external-service adapter. Every form remains behind Miaoxun
authentication, authorization, audit, budgets, lifecycle, artifacts, Admin controls, and client contracts.

## 14. Truthful Status

Creator-controlled states: `local-draft`, `locally-checked`, `creator-sealed`, `submitted`.

Platform-controlled states: `accepted-for-review`, `changes-requested`, `integration-in-progress`,
`sandbox-ready`, `release-approved`, `published`, `paused`, `retired`.

A file, registry row, receipt, test score, mock response, HTTP 200, or reviewer comment cannot be promoted
to a later state without the corresponding authority and evidence.
