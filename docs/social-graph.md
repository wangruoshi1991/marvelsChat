# 社交关系流程

这份文档定义妙讯里“扫码看主页、关注、加好友、通知、隐私设置”的统一流程。

## 目标

- 扫码后直达用户主页或小站主页。
- 主页内支持关注、加好友、查看粉丝、关注中、收藏。
- 好友申请和关注行为进入通知与未读体系。
- 搜索、最近搜索、关系状态和主页可见范围彼此一致。
- 隐私设置必须能控制别人能看到什么。

## 当前事实

- 后端已建立用户、资料、会话、消息、事件、Agent 运行、社交关系、好友申请、通知、搜索历史和主页可见范围表。
- 扫码结果会调用 `/api/scan/resolve`，由后端解析 AI ID 并返回公开主页、关系状态和可见性处理后的字段。
- 当前已支持关注、取消关注、发送好友申请、通过好友申请、通过后自动生成双方好友聊天线程、新关注/好友申请/好友通过通知、通知未读、关注/粉丝/好友列表、用户搜索、最近搜索和主页展示开关。扫码、用户搜索、好友列表、关注列表、粉丝列表和好友聊天页都进入同一套公开主页；扫码不是查看或关注用户的唯一入口。
- 尚未实现签名动态码落库校验、好友拒绝/取消、收藏列表、内容级可见范围和推送偏好。

## 建议流程

### 1. 扫码

- 用户扫到的是一个可解析的主页标识。
- 推荐内容不是纯裸 AI ID，而是带签名和过期时间的短效 payload。
- 扫码成功后先由后端解析，再决定能否打开主页。
- 相机扫码页识别成功后会自动关闭；客户端进入主页解析状态并等待 `/api/scan/resolve`，不能停在没有反馈的空白或旧页面。
- 扫码只负责打开对方公开主页，不直接创建好友关系。
- 客户端只接受 `miaoxun://ai/<12位AI ID>` 或裸 12 位 AI ID 作为主页扫码结果；其他二维码必须直接提示无效，不进入主页解析加载。
- 过期、无效、无权限都要明确报错，不做静默跳转。

### 2. 主页

主页分三层：

1. 公开信息：头像、昵称、简介、社区、活动区域、AI ID。
2. 关系信息：关注数、粉丝数、收藏数、关系状态。
3. 可见内容：动态、相册、日记、音乐、文件，按隐私范围决定展示。

### 3. 关系动作

- `关注 / 取消关注`：单向订阅，适合看公开内容；取消关注只删除 `follow` 关系，不影响已经成立的 `friend` 关系。
- `加好友`：双向关系，需要申请和确认。
- `收藏`：只对内容项生效，不等于关系。

当前阶段好友申请只从公开主页发起；公开主页可由扫码、搜索、好友列表、关注列表、粉丝列表和好友聊天页进入。妙讯页 `+` 菜单展示独立添加好友和创建群入口，但两者处于待接入状态，不触发后端写入。关注、取消关注和加好友都必须有明确提交中状态。接口成功后更新当前主页关系状态并刷新关系/通知数据；接口失败或超时后恢复按钮并展示错误，不允许让页面长期保持不可交互状态。

好友通过后的闭环：

1. A 通过扫码或搜索打开 B 的公开主页。
2. A 点击 `加好友`，后端创建 `social_requests`，B 的通知列表出现好友申请并计入未读。
3. B 在妙讯页通知中点击 `通过`，后端写入双向 `friend` 关系，并为 A/B 两侧各创建一个 `chat_threads.peer_user_id` 指向对方的 direct 线程。
4. A/B 的妙讯聊天列表和小站社交页好友列表都会出现对方；好友列表里点击头像/资料区域进入公开主页，点击消息图标进入 direct 聊天；聊天页右上角资料入口也进入同一公开主页。在公开主页已是好友时显示 `发消息`。
5. 任一方发送 direct 消息时，后端同时写入对方的对应线程并增加对方线程未读数；消息 metadata 中的 `senderUserId` 必须始终是实际发送者，不能被接收方线程覆盖。妙讯管家线程仍只走 Agent 链路。
6. 在线 direct 消息通过 `/api/realtime` WebSocket 推送到对方设备；实时连接按登录 token 生命周期保持，不因打开或关闭聊天页、收到 `presence.changed` 或更新本人 `presenceMode` 而重建。异常断开后客户端只重连同一个 WebSocket 通道，离线期间遗漏的消息由后续 bootstrap/sync 补齐，不使用轮询伪装实时聊天；聊天页顶部不展示实时连接说明文案，用户只在发送失败、重试或同步结果变化时看到具体操作状态。用户自己的在线模式从小站顶部名称处切换，后端只接受 `online / offline / hidden`；别人只能看到公开状态 `online / offline`，其中 `hidden` 和主动 `offline` 都公开为离线。WebSocket 连接上线、最后连接断开和在线模式切换都会向好友、关注关系和 direct 聊天相关用户推送 `presence.changed`，客户端收到后直接更新聊天列表和社交列表里的公开在线状态，再通过增量同步补齐遗漏数据，不能用整包 bootstrap 触发实时连接重建。
7. 客户端发送消息时先展示内存态本地气泡；后端写入成功后用真实 `chat_messages` 记录替换，失败时标记为“发送失败，点击重试”。失败消息不能写入后端，也不能计入对方未读。
8. 回复、复制、删除和撤回是长按消息的基础动作，操作入口必须显示在被选消息附近，不能用固定底部工具条代替。复制只进入系统剪贴板，不写后端；回复、删除和撤回必须走后端状态。回复写入 `metadata.replyTo` 快照；删除设置当前用户线程内消息 `deleted_at`，不影响对方线程；撤回仅允许发送者在发送后 1 分钟内执行，撤回窗口由 PostgreSQL 的 `created_at` 和 `CURRENT_TIMESTAMP` 判断，设置同一 `client_message_id` 下双方消息 `recalled_at` 并通过 WebSocket 推送 `thread.message.updated`。没有 `client_message_id` 的历史消息或超过 1 分钟的消息不能撤回，避免只在单侧生效。
9. 聊天时间不挂在每条气泡下方；客户端按消息流展示居中时间分隔条，第一条真实消息显示时间，后续间隔 5 分钟及以上再显示。
10. 切换中英文只影响 UI 文案、状态、操作错误和本地妙讯管家动作结果；真实聊天正文和历史消息按发送时内容展示，不在客户端自动翻译或改写。
11. 妙讯页聊天列表保留点击进入，同时支持左滑进入对应聊天页；聊天页支持左滑退出到妙讯页，并保留左上角 `<` 返回。滑动动画必须跟随手指横向位移，释放时按距离或速度触发，不用只移动几十像素的假反馈。

建议优先级：

1. 关注
2. 加好友
3. 聊天

原因是关注最轻，好友次之，聊天需要更明确的关系边界。

### 4. 通知与未读

通知建议统一进入妙讯页的“通知”列表，和系统消息同屏展示。

典型通知：

- 好友申请
- 好友通过
- 新关注
- 主页隐私变更
- 内容收藏提醒
- 系统审核或权限变更

每个通知都应写入未读数，未读数可同步到妙讯页角标和通知列表。进入通知页只表示查看列表，不自动把全部通知设为已读；用户点击单条通知、点击“标记已读”或处理好友申请后，才调用单条已读接口。`usage_events` 和 `agent_runs` 只用于后台审计与运行记录，不混入 App 通知列表。

### 5. 搜索

妙讯页搜索建议支持：

- 用户
- 会话
- Agent
- 未来可扩展到动态和文件

搜索历史建议保存最近若干次，作为“最近搜索”。这是产品记忆，不是聊天记忆，最好独立保存。

## 隐私设置

建议把可见性拆成明确开关，而不是一个总开关：

- 主页简介是否可见
- AI ID 是否可见
- 粉丝列表是否可见
- 关注列表是否可见
- 收藏是否可见
- 动态是否可见
- 相册是否可见
- 日记是否可见
- 音乐是否可见
- 文件是否可见

可见范围建议至少支持：

- 公开
- 平台内所有人
- 粉丝
- 好友
- 仅自己

## 已落地数据模型

- `social_relationships`
- `social_requests`
- `notifications`
- `search_history`
- `profile_visibility`
- `chat_threads.peer_user_id`

`showFollowingList` 和 `showFollowersList` 已作为独立隐私字段落库；当前 App 只允许用户查看自己的关注/粉丝列表。后续如果开放查看他人关注/粉丝列表，必须先增加受这些字段约束的公开列表 API，不能从前端绕过隐私设置。

## 页面落点建议

- 妙讯页：聊天 / 通知

- 设置页：隐私开关、通知设置、可见范围
- 搜索页：全局搜索和最近搜索

## 约束

- 不用假数据闭环。
- 没有表、没有 API 的能力只保留入口和明确待接入状态。
- 扫码、主页、关注、隐私必须统一在后端校验，不在前端偷偷兜底。
