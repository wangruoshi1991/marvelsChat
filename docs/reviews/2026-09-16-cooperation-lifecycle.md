# 第一面合作与评分业务契约

日期：2026-09-16。状态：实现依据已明确，本文为待实现契约；尚未创建合作数据表、API 或客户端流程，尚未部署。

## 已确认的产品口径

用户已确认：第一面的“合作伙伴 / 综合评分”按**完成的合作与合作后的评价**计算。这项来源决定不再重复请求确认。

第一面的三个指标为“粉丝 / 合作伙伴 / 综合评分”。粉丝继续来自真实关注关系；合作伙伴和评分使用独立业务数据，不复用关注数、点赞数、收藏数、好友数或 AI 伙伴数量。

设计稿展示 `4.9`。本轮采用五分制：每次评价提交 1–5 的整数分，聚合后显示一位小数，并在评分详情标明“满分 5 分”和有效评价数量。`4.9` 是设计示例，绝不作为初始值。

本模块记录双方自愿确认的合作及评价，不代表平台核验了线下履约，也不建立订单、交易、托管、付款、退款、收入或违约赔偿义务。后续如引入交易，需要独立定义相应契约。

## 用户流程与状态

合作限两名不同的有效注册用户。用户从他人个人页或现有会话的明确入口发起合作，填写标题和约定说明；不由妙讯管家、聊天关键字或后台替用户自动接受。

| 当前状态 | 操作者及动作 | 结果 |
|---|---|---|
| 无记录 | 发起方创建邀请 | `pending`，通知接收方 |
| `pending` | 接收方接受 | `active`，记录双方身份及接受时间 |
| `pending` | 接收方拒绝 | `declined`，记录原因 |
| `pending` | 发起方撤回 | `withdrawn` |
| `active` | 任一方申请完成 | `completion_requested`，记录申请人并通知另一方 |
| `completion_requested` | 另一方确认完成 | `completed`，记录确认人和完成时间，开放双方评价 |
| `completion_requested` | 另一方拒绝完成 | `active`，必须填写原因 |
| `active` | 任一方申请取消 | `cancellation_requested`，通知另一方 |
| `cancellation_requested` | 另一方同意取消 | `cancelled` |
| `cancellation_requested` | 另一方拒绝取消 | `active`，必须填写原因 |

`declined / withdrawn / cancelled / completed` 是用户流程终态。终态不可由客户端任意回退。没有超时自动接受、自动完成或自动取消；申请没有被确认时，明确显示等待对方处理。

完成请求与取消请求互斥。请求方可撤回自己的待处理请求，回到 `active`；撤回与对方确认发生竞争时，只能有一个事务成功。已完成记录出现问题走申诉及管理员有效性处理，不覆盖原有完成事实。

接受前如需修改约定，撤回原邀请后重新发起；接受后不允许单方修改标题、约定或参与方。首版不加入条款变更协商流程。

## 评价与统计

每条有效且已完成的合作，双方各有一次评价对方的资格。服务端根据登录用户和合作参与方推导被评价用户，客户端不能自由指定目标。评价内容为整数分数及可选文字；提交后用户不可直接修改分数或删除记录，纠错通过申诉处理。

- `partnerCount`：存在至少一条 `completed` 且管理有效性为 `valid` 的合作记录的不同对方用户数。同一用户合作多次只计一个伙伴。
- `reviewCount`：本人收到的有效评价条数，要求对应合作有效且已完成，评价状态为 `visible`。
- `score`：上述评价分数的算术平均值，由服务端统一四舍五入到一位小数；没有有效评价时为 `null`，客户端显示“暂无评分”，不显示 `0.0` 或满分。
- 一名伙伴多次完成合作可以产生多条评价。详情说明“按有效合作评价计算”，使评价数与去重伙伴数的区别可理解。
- 合作有效性与评价展示状态分离。作废合作后，其伙伴关系贡献和关联评价都不计入统计；恢复后重新计入符合条件的数据。仅隐藏违规评价不会取消真实合作形成的伙伴关系。
- 发起申诉本身不自动改变统计，避免一方通过反复申诉隐藏低分。只有有权限的管理员依据明确原因完成处理后才改变有效性。

资料 API 增加独立对象，保留现有指标含义：

```ts
type CooperationStats = {
  partnerCount: number;
  score: number | null;
  reviewCount: number;
  scoreScale: 5;
};
```

本人资料返回 `cooperationStats: CooperationStats`。公开资料受现有 `showCounts` 控制：不可展示时整个 `cooperationStats` 为 `null`；真实没有合作时返回 `{partnerCount: 0, score: null, reviewCount: 0, scoreScale: 5}`。隐藏、真实零值与请求失败不得混为一谈。新接口字段必须真实存在；客户端不通过缺失字段填零来掩盖未部署的服务端。

首版直接查询关系表计算统计，并建立查询索引，不增加手工维护的汇总字段或缓存。所有本人和他人资料入口使用同一个聚合实现，避免计算规则分叉。

## 访问与隐私

合作标题、约定、时间线、申诉材料及评价文字默认只给参与双方和有明确权限的管理员查看。公开个人页只展示上述聚合统计；不因“评分公开”就公开合作详情或私人说明。首版评分详情可以说明量表、样本数量与规则；公开评价文字、合作对方名单属于后续单独的展示契约。

所有读取和写入先验证登录及参与方身份。非参与者无法枚举记录详情；后台使用专用权限。禁止自己邀请自己，禁止冒充接受、完成确认或评价。双方账号必须处于有效状态；如已有明确屏蔽关系，不允许发起新邀请。

发起邀请、申诉及状态操作接入现有服务端限频机制；服务端做字段长度和枚举校验。约定和评价是用户内容，显示时作为纯文本处理。产品错误必须明确，不在失败时显示成功状态。

## 数据与事务边界

沿用现有 Node.js 模块化后端与 PostgreSQL。迁移 `031` 留给本轮个人身份资料变更；合作迁移使用落地时下一个未占用编号，**不得早于 `032`**。本契约不创建或预占实际 SQL 文件。

建议实体：

| 实体 | 必需字段与约束 |
|---|---|
| `station_cooperations` | ID、发起人/接收人、标题、约定、流程状态、当前请求人、版本号、接受/完成/创建/更新时间；参与方不同；管理有效性 `valid/invalid` 与流程状态分离 |
| `station_cooperation_reviews` | 合作 ID、评价方身份、整数分数 1–5、文字、`visible/hidden`、创建时间；每条合作每方至多一条评价 |
| `station_cooperation_events` | 合作 ID、操作者、动作、前后状态、原因、时间、幂等关联；追加写入，不覆盖历史 |
| `station_cooperation_disputes` | 合作 ID、可选评价 ID、申诉方、类型/说明、`open/resolved/rejected`、处理人/结论/时间；同一方同一对象不可重复创建未结束申诉 |

对参与方、状态和时间建立组合索引；评价按合作及被评价方查询；申诉按状态/时间查询。用户关联沿用当前账号删除机制：删除账号时级联清除关联合作、评价和私有材料，剩余用户统计由实时聚合自然更新。若未来保留匿名历史，需要先独立定义匿名化及保留期限，不能默认保留个人内容。

每次状态迁移在一个事务内锁定合作记录，检查当前状态、请求人、登录身份和客户端 `expectedVersion`，然后写入新状态、事件与通知。竞争操作只有一个成功，失败者获得明确的 `409` 和可重新获取的最新状态。

创建邀请、状态迁移、评价、申诉及后台变更要求幂等键。相同操作者/操作/键且请求内容一致时返回已完成结果；键相同但请求内容不同返回冲突。幂等结果持久化，不能只依赖客户端按钮禁用或进程内缓存。

现有 `notification-service.js` 使用全局 `query`，需要明确增加事务执行器接口，使业务写入、通知和事件一起提交。提交成功后再发送实时刷新；实时连接失败不回滚已成功的业务，也不伪造即时送达，用户刷新后能读到持久化通知。

## API 契约

沿用现有 Bearer 认证与 `{data: ...}` 响应结构：

- `GET /api/station/cooperations`：本人参与记录，支持状态筛选及游标分页。
- `POST /api/station/cooperations`：创建邀请，包含 `targetUserId / title / terms`；返回记录和版本。
- `GET /api/station/cooperations/:id`：详情、本人角色、服务端计算的可执行动作；不能仅靠客户端推导权限。
- `POST /api/station/cooperations/:id/actions`：受限动作枚举、`expectedVersion`、必要原因。动作包含接受、拒绝、撤回邀请、申请/确认/拒绝/撤回完成请求、申请/确认/拒绝/撤回取消请求。
- `POST /api/station/cooperations/:id/review`：提交 `score / comment`；服务端校验资格并推导评价目标。
- `GET /api/station/cooperations/:id/events`：参与双方可读的时间线，游标分页。
- `POST /api/station/cooperations/:id/disputes`：提交合作或评价申诉；同一事务写入事件及后台待办。

具体请求字段限制、稳定业务错误码、幂等键请求头以及分页格式在编码前写入共享契约/Schema，并由客户端、服务端和测试共同使用。无权访问或记录不存在不泄露参与方信息；状态不匹配、重复评价、幂等冲突为明确的业务冲突。

## 后台管理闭环

新增 `cooperations:read` 与 `cooperations:moderate` 权限，进入现有权限分配及鉴权机制。只读人员可查合作列表、详情、有效性、评价及时间线；有处理权限的人员可处理申诉。

后台支持按用户、业务状态、有效性及待处理申诉筛选。必要操作为：有理由地作废/恢复合作，隐藏/恢复违规评价，解决或驳回申诉。每次变更都要求原因、版本校验、操作者与时间，并通知双方。

后台不能直接填伙伴数或综合评分，不能改用户给出的原始分数，不能替任何用户点击接受或完成。审核结果影响统计时，应在详情明确展示原因和影响范围。运营审计保留必要行为信息，不将私有约定或申诉全文复制到通用日志。

## 可执行验收

- 两个普通用户完成邀请、接受、申请完成、另一方确认、双方评价；双方状态一致，通知能直达详情，刷新和重新登录后数据一致。
- 自我邀请、非参与者读取/写入、冒充对方确认、未完成评价、评价错误目标、重复评价均被服务端拒绝。
- 未获对方完成确认时伙伴数不增长；拒绝完成/取消后回到进行中；没有自动完成逻辑。
- 完成确认与取消/撤回并发时只有一个成功；重复请求不会产生重复合作、评价、事件或通知；幂等键内容冲突可被识别。
- 一次完成合作使双方伙伴数各加一；同一对方再次完成不重复增加伙伴数；新增不同对方增加一。
- 无评价 `score=null`；评分 4、5 的有效样本得到 4.5；非法分值/小数被拒绝；隐藏评价后重新计算；样本全被隐藏后恢复 `null`。
- 管理员作废合作后，其统计贡献及关联评价不计入；恢复后重新计入；仅隐藏评价不删除伙伴关系；原始用户分值保持不变。
- 申诉创建本身不改变统计；缺少后台权限或审核原因的操作失败；处理结果有可追溯审计并通知双方。
- `showCounts=false` 时公开 API 和界面不泄露合作统计；合作私有文本/评价文字不出现在公开资料、无权限接口或通用日志。
- 账号删除能完成关联清理，另一方统计重新计算；不留下不可访问却仍计分的孤立记录。
- 数据迁移能在空库和已有数据测试库执行，外键/唯一性/评分检查约束真实生效；数据库迁移未应用时不宣称服务就绪。
- App 与后台实际交互检查覆盖加载、空数据、拒绝、冲突、错误、重复点击、长文本、小屏与通知返回路径。单元测试通过不等于真机或上线验收通过。
