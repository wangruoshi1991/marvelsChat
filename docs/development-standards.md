# 妙讯开发规范

## 上线目标

妙讯按正式上架产品开发。代码、文案和交互必须服务于可维护、可验证、可上线的实现，不做看起来能跑但实际不可交付的临时功能。

## 功能边界

- 未接入数据库表、后端 API、权限策略和审核流程的功能，只能展示真实空状态或不展示入口。
- 不写假聊天、假列表、假地址、假文件、假封面、假数量或假已接入状态。
- 配置缺失、权限拒绝、网络失败、后端错误必须明确提示，不静默回退到示例数据。
- 新能力先定义数据结构、接口契约、错误状态和权限边界，再接 UI。

## 代码结构

- 屏幕文件只负责页面编排、路由状态和数据传递；业务分区组件放在同 feature 目录下的独立文件。
- 一个文件持续超过约 300 行时，应优先拆分为容器、区块组件、共享组件、类型定义或服务层。
- 通用 UI 只放真正跨模块复用的组件；不要把单个业务模块的细节塞进全局共享文件。
- 业务逻辑不得混入样式文件；样式文件不得承载数据、权限或状态判断。

## 数据与状态

- 客户端只能展示后端返回的真实业务数据、本地输入中的临时状态，或明确标注的待接入状态。
- 发送中、失败、重试等本地状态必须和后端最终消息区分，不能伪装成已送达。
- Agent、虚拟形象、日记、相册、文件等长期功能必须有审计、权限和持久化方案后再做正式入口。

## 变更要求

- 删除低质量功能优先于继续包装低质量功能。
- 修问题时解决根因；兼容、兜底和降级只能用于明确的真实边界，不能掩盖配置或实现缺失。
- 每次较大改动后至少执行 TypeScript 检查和 diff 空白检查。
